# Release map

Generated by `db/tools/release_map.py` from the built database (audit T3-06); do not edit by hand.

**What goes to production.** The whole schema is installed in every environment, so upgrades stay linear and tested. A release goes into **service** only when its switches are on:
- **Tables:** every table of a phase whose switches are off is closed by a restrictive `phase_gate` policy, so no company can read or write it.
- **Application:** the endpoints of a switched-off module answer 404.
- **Workers:** they act only on rows that exist, and a closed phase has none.

**Launch scope:** releases **1A** and **1B**. Every later phase stays switched off until it passes its own acceptance gate (security, privacy, capacity, recovery, runbooks).

## Closed until switched on

92 tables carry a `phase_gate` policy. Tests that prove a closed phase stays closed:
- **Database:** `db/tests/run_tests.sql`, audit R-14. Every table of a switched-off phase is closed, and a company reads and writes nothing of it.
- **Application:** the module framework tests (`backend/tests/test_modules.py`). A switched-off module's endpoints answer 404.

## Ownership

Each owning team answers for its schemas' data, migrations (with the plan in `docs/database/MIGRATION_PLANS.md`), alerts and on-call. Changes that cross two teams' schemas need both teams' review. The two-way dependencies between schemas are frozen by test H-07: a new one fails the build.
