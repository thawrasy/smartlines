# التجهيز قبل اختيار الخادم (الصف 56 في `docs/31`)

التاريخ: 2026-10-25. كتبه وكيل ذكاء اصطناعي.

## 1. ما طلبه المالك

«اكمل وجهّز ما يمكن تجهيزه قبل اختيار الخادم».

## 2. ما صار جاهزًا

| ما جُهّز | ماذا يفعل | كيف تحقّقنا منه |
|---|---|---|
| **ملف قيم واحد** (`tools/host/site.conf.example`) | كل قيم خادمكم في مكان واحد: النطاق، وخادم القاعدة، والبريد، ومزوّد DNS، والصورتان، واسم المفتاح | — |
| **سكربت تجهيز خادم التطبيق** (`tools/host/provision_app_host.sh`) | يكتب من ملف القيم: المجلدات بصلاحياتها، والمفتاح الرئيسي مرة واحدة دون استبدال، وملفات الإعداد، و`compose.yml`، وCaddyfile، ويضع الأسرار في أماكنها. وإعادة تشغيله آمنة | جُرّب في مجلد اختبار؛ لم تبقَ قيمة ناقصة، وملف `compose.yml` الناتج صالح |
| **فحص جاهزية خادم التطبيق** (`tools/host/check_ready.sh`) | يقرأ فقط ولا يغيّر شيئًا. يفحص نحو 30 بندًا: صلاحيات الملفات والأسرار، ووضع الإنتاج، وغياب أي إعداد تجريبي، وقائمة كلمات المرور، والصورتين، وCaddy، والجدار، وDNS، والوصول إلى القاعدة والبريد | جُرّب، ويُظهر ما ينقص بوضوح |
| **فحص جاهزية خادم القاعدة** (`tools/deploy/check_db_host.sh`) | يقرأ فقط. يفحص إصدار النظام وSQL Server مقابل `versions.json`، وفرض التشفير، والشهادة وصلاحيتها، والمجلدات، والجدار (1433 غير مفتوح للعموم)، وSSH | جُرّب على ملفات تجريبية |
| **دعوة المشغّل الأول** (`tools/deploy/bootstrap_operator.sh`) | الخطوة D-10 من `docs/54` | جُرّب على قاعدة محلية |
| **بناء الصورتين في GitHub** | مع كل تعديل يبني GitHub الصورتين بشبكة حقيقية، ويجرّب تنزيل Chromium الذي كان محجوبًا عندنا. ثم يشغّل التشغيل التجريبي كاملًا على قاعدة جديدة منشورة كما في الإنتاج | **أول تشغيل كشف خللًا** كان سيمنع بناء صورة الخادم على أي خادم بلا وكيل شبكة، فأُصلح. **والتشغيل التالي نجح كله** في 2026-10-25: البناء، وفحص القوالب، ونشر القاعدة، واختبار المتصفح على الحاويتين ([التشغيل 167](https://github.com/thawrasy/smartlines/actions/runs/40191933042)) |

## 3. معايير اختيار مزوّد الخادمين

| المعيار | المطلوب | لماذا |
|---|---|---|
| الدولة | **في الدولة التي تعتمدها**، مع عقد معالجة بيانات | DQ-S07-1، وDOC-S07 §9 |
| نظام التشغيل | صورة **Ubuntu 24.04 LTS** الرسمية | يرفض النشر غيره (`versions.json`) |
| عدد الخوادم | **اثنان**، يفضَّل بينهما شبكة خاصة | القرار 6 |
| العنوان | IPv4 ثابت لكل خادم | سجلات DNS وقاعدة الجدار على خادم القاعدة |
| الحجم المقترح للتطبيق | 4 معالجات، 8 غيغابايت ذاكرة، 100 غيغابايت قرص | الحاويات وChromium وClamAV وقائمة كلمات المرور |
| الحجم المقترح للقاعدة | 4 معالجات، 16 غيغابايت، وأقراص منفصلة للبيانات والسجل والنسخ والتدقيق، أو قرص كبير يُقسم | DOC-S10 §3 |
| الجدار الشبكي | جدار من لوحة المزوّد، طبقةً ثانية | DOC-S10 §6.2 |
| اللوحة | **مصادقة متعددة** لكل حساب، وتحكّم في اللقطات التلقائية | DQ-S09-6 |
| تشفير الأقراص | تشفير المزوّد للأقراص عند التخزين | DOC-S02 |
| المنفذ 587 للخروج | مسموح، فبعض المزوّدين يحجب البريد | البريد من الخادم والخادم الخلفي |
| موقع النسخ الاحتياطي | مكان منفصل عن الخادمين: مزوّد آخر، أو منطقة أخرى | DOC-S09 |
| الدعم | استجابة واضحة للأعطال، ونافذة صيانة معلنة | التشغيل |

**أسئلة تُطرح على المزوّد قبل التعاقد:**
1. هل تتوفر صورة Ubuntu 24.04 الرسمية، وهل تبقى أنويتها هي أنوية Ubuntu؟
2. هل توجد شبكة خاصة بين خادمين في الموقع نفسه، وهل هي مجانية؟
3. هل المنفذان 25 و587 للخروج مفتوحان أم يُفتحان بطلب؟
4. أين تُحفظ اللقطات والنسخ، وهل يمكن تعطيلها أو تشفيرها؟
5. هل توجد مصادقة متعددة وصلاحيات مستقلة لكل مستخدم في اللوحة؟
6. ما سياسة الوصول إلى بيانات العميل، وهل يوجد عقد معالجة بيانات؟

## 4. نموذج القيم المطلوبة منكم

تُملأ هذه القيم مرة واحدة، فتصير ملف `site.conf` وملفات خادم القاعدة:

| القيمة | مثال | من يوفّرها |
|---|---|---|
| النطاق | `treasury.company.com` | المالك |
| مزوّد DNS ورمز API له | Cloudflare | المالك أو OPS |
| اسم خادم القاعدة في الشهادة | `db.treasury.company.com` | OPS |
| خادم البريد ومنفذه وحسابه وعنوان المرسل | `smtp.office365.com`، 587 | المالك |
| بريد التشغيل وبريد التنبيهات الأمنية | `ops@...`، `security@...` | المالك |
| عناوين IP للمسؤولين | `203.0.113.10/32` | OPS |
| إصدار SQL Server المرخَّص | Standard | المالك |
| المكان الآمن للمفتاح الرئيسي وشهادة TDE، ومن يطّلع عليه | خزنة كلمات مرور للمؤسسة، وشخصان | المالك |
| موقع النسخ الاحتياطي المنفصل | حاوية تخزين عند مزوّد آخر | المالك مع OPS |

## 5. ما يبقى بعد اختيار الخادم

بالترتيب، وكل خطوة في `docs/54`:
1. **خادم القاعدة:** الجزء B، ثم `check_db_host.sh`.
2. **نشر القاعدة:** الجزء D، ومنه دعوة المشغّل الأول.
3. **خادم التطبيق:** الجزء H، بملف القيم و`provision_app_host.sh`.
4. **التشغيل وأول استعمال:** الجزء R، بعد أن يخرج `check_ready.sh` بصفر.
5. **اختبار القبول:** مع مستخدم من الخزينة (DOC-B12).

والمهمة الجديدة في GitHub (`images` في `treasury-db-ci`) تتحقق مع كل تعديل من أن الصورتين تُبنيان وتعملان. فما يُنشر على الخادم مجرَّب قبل وصوله.
